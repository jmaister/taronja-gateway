# Release Notes: v1.0.0

**Since:** v0.0.24 (the last tagged release before this one — 80+ commits,
spanning the middleware refactor and everything else that landed alongside
it on the same branch).

This is a big release. Nothing here breaks an existing `config.yaml` —
every new feature is opt-in, and the config schema version stays at `1`
(see [Config File Versioning](../README.md#config-file-versioning); a v2
schema was drafted mid-refactor and deliberately renumbered back to v1
before release, since nothing in this cycle actually needed a breaking
config change). The sections below group what's new by area; each links to
the full reference for the details that don't belong in a release-notes
summary.

## Authentication

Three new OAuth2 providers, alongside the existing Google/GitHub/Basic:

- **Microsoft (Entra ID / Azure AD)** — optionally restricted to one
  tenant/organization.
- **Facebook.**
- **Apple ("Sign in with Apple")** — the odd one out: Apple never issues a
  static client secret, so the gateway signs a short-lived JWT itself on
  every login, and verifies the returned ID token's signature against
  Apple's real JWKS (rotated automatically in the background).

See [README.md § Authentication Providers](../README.md#authentication-providers)
for setup instructions per provider.

## Networking

- **TLS termination (HTTPS)**, two ways: your own certificate files
  (hot-swapped with zero downtime the moment something else renews them —
  `certbot` or similar keeps doing the actual renewal), or fully automatic
  certificates via **ACME / Let's Encrypt**, with no external tool at all.
  Either way, enabling TLS also turns on **TLS-level JA4 fingerprinting**
  for free — a more stable client signal than the HTTP-header-based
  fingerprint, since it's computed once per connection from the real TLS
  handshake instead of per request. See
  [README.md § TLS / HTTPS](../README.md#tls--https).
- **Load balancing** — give a route's `to` a list of backend URLs instead
  of one, and requests spread round-robin across them, with automatic
  failover to the next backend on a connection-level failure. See
  [README.md § Load Balancing](../README.md#load-balancing).
- **Distributed tracing** via OpenTelemetry/OTLP — one span per request,
  continuing an incoming `traceparent` and propagating it to whatever
  backend a proxy route calls, so a trace can span the whole journey. See
  [doc/middleware/tracing.md](middleware/tracing.md), which includes a
  "try it locally against real Jaeger" walkthrough.
- **Response compression** — brotli, zstd, gzip, and deflate, negotiated
  per request from `Accept-Encoding`, with no configuration beyond turning
  it on. See [doc/middleware/compression.md](middleware/compression.md).
- Fixed a bug where a broken/unreachable backend could hang a proxied
  request indefinitely instead of returning `502 Bad Gateway`.

## Notifications (new)

An entirely new system: the gateway can store and deliver notifications on
behalf of the app(s) it sits in front of, so each one doesn't need to build
its own notification list, SMTP integration, or Telegram bot.

- **In-app, email, and Telegram** delivery, chosen per user (each
  recipient can set their own preferred channel) or forced per call.
- **Multi-recipient `Create`** — one call notifies a whole list of users,
  each getting an independent record, all sharing one batch ID.
- **Automatic retries with backoff** on delivery failure, with the full
  attempt history kept (not overwritten) for each channel.
- **Computed status** — sent/failed/pending, both per notification and
  rolled up across a whole batch — derived on demand from the delivery
  history rather than stored redundantly.
- **An outbound, HMAC-signed webhook** fired when a user responds to a
  notification (via web, email link, or Telegram button), so the calling
  app doesn't have to poll for that.

See [doc/notifications.md](notifications.md) for the full data model, API
reference, retry schedule, and the email answer-link/Telegram
account-linking flows.

## Rate limiter

- **Persistent block-event history** — every time an IP gets blocked, it's
  now recorded permanently (reason, matched path, geo/fingerprint data),
  independent of the in-memory tracker's own cleanup, answering "was this
  IP blocked last week, and why."
- **A per-country attacker map** on the admin dashboard's Rate Limiter
  page, built from that same history.

See [doc/middleware/rate-limiter.md](middleware/rate-limiter.md).

## Analytics

- **Traffic-over-time graphs** — requests, unique visitors, errors, and
  latency, bucketed by minute/hour/day/week/month, computed SQL-side.
- **New-vs-returning visitor** breakdown, using the consolidated
  fingerprint (see below).
- **One consolidated `fingerprint`/`fingerprintType` pair** replacing the
  previous three separate fingerprint columns (JA4H, TLS-JA4, a
  reduced-entropy "stable" fingerprint) — whichever signal is most
  reliable for a given request wins, exposed as a single field everywhere
  (`X-User-Data`, the admin dashboard, the API). See
  [doc/middleware/ja4-fingerprint.md](middleware/ja4-fingerprint.md).
- Every timestamp in the schema is now stored as UTC consistently (it
  wasn't, before this release, for anything outside `TrafficMetric`), with
  a versioned data-migration mechanism (`db/migrations.go`) that backfills
  a database's existing rows the first time it's opened by this version.
- Fixed a bug where private/loopback/link-local client IPs (e.g.
  `192.168.x.x` behind a reverse proxy) were still sent to the public geo
  IP lookup API, which could only ever fail for them.
- Client IP trust is now a zero-config heuristic instead of a
  `server.trustedProxies` config list — see
  [AGENTS.md](../AGENTS.md) for the reasoning (found via a real JNDI-probe
  attempt logging its own spoofed IP as the "client IP").

## Middleware architecture

The gateway's global middleware chain (compression, CORS, rate limiting,
JA4 fingerprinting, session extraction, traffic metrics, logging, tracing)
is now built from a declarative Factory + Registry system instead of
hardcoded conditionals — every existing config file behaves identically
unless you opt into the new pieces. See
[README.md § Middleware Architecture](../README.md#middleware-architecture)
and [doc/refactor01-release-notes.md](refactor01-release-notes.md) for the
full write-up (this is the refactor the branch was originally named for).

Highlights:

- An optional, explicit `middleware:` YAML section for declaring the chain
  in order, alongside the legacy flags (which still work unchanged).
- `GET <prefix>/api/middleware` / `.../metrics` — runtime status, health,
  and per-middleware request metrics.
- `tg middleware list --config <path>` — the same status, offline, without
  starting the server.
- A documented, tested extension path
  ([doc/middleware_development.md](middleware_development.md) +
  [`examples/middleware-plugin/`](../examples/middleware-plugin/)) for
  adding a middleware with no changes to the gateway's own source.

## Config and operations

- **Config file schema versioning** — a config declares `version: N`; the
  gateway refuses to start against one older than it requires and tells
  you to run `tg migrate` instead of silently reinterpreting it.
- **Hot config reload** — edit `config.yaml` and save (or send `SIGHUP`)
  to pick up new routes/middleware/rate-limiter settings with no restart;
  `.env` is re-read too. Fields that need a real restart (`server.host`/
  `port`, TLS settings, tracing settings, notification settings) log a
  clear warning instead of silently no-opping.
- **`tg validate`** — load and validate a config file (schema version,
  routes, admin settings, the middleware dependency graph) with no server,
  database, or network access — safe for CI.
- **`make fullbuild`** — one target mirroring CI's full build+test+lint
  gate (Go, webapp, SDK), including a check that generated files
  (`api/api.gen.go`, `doc/CONFIG.md`) are byte-identical to what's
  committed.

## Upgrading

Drop in the new binary; no config changes are required. If you're
upgrading from a database older than v0.0.24 specifically, `applyDBMigrations`
runs automatically on first startup — see
[AGENTS.md](../AGENTS.md) for what it covers and
[db/testdata/README.md](../db/testdata/README.md) for how that's tested
against a real historical database.
